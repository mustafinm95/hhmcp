# HH MCP v1 для соискателя

Локальный MCP-сервер для Windows 10/11, macOS и Linux. Он ищет вакансии, читает карточки и справочники,
показывает собственные резюме и историю откликов и создаёт неизменяемые локальные
черновики отклика. Сервер работает по `stdio` и не содержит собственного LLM.

`hh_submit_application` намеренно не опубликован. В доступной конфигурации MCP не
подтверждена граница, на которой решение о конкретной отправке принимает человек вне
контроля модели. Отправка есть только в отдельной ручной CLI-команде и не является
защитой от ассистента или другого процесса с доступом к shell/PTY от имени пользователя.

## Что входит в v1

- расширенный поиск с одной явно выбранной страницей (до 100 результатов, глубина HH
  до 2000);
- карточки вакансии и работодателя;
- справочники областей, ролей, метро, отраслей и фильтров;
- чтение только собственных резюме; контакты скрыты по умолчанию;
- чтение истории и одной карточки отклика/приглашения, без переписки;
- подготовка зашифрованного AES-256-GCM-черновика на 24 часа;
- устойчивый SQLite-журнал и атомарная блокировка повторной отправки по
  `(account_id, vacancy_id)` между черновиками, процессами и перезапусками;
- OAuth Authorization Code + PKCE S256, одноразовый refresh и единый lock для login,
  refresh и logout.

Создание и изменение резюме, переписка, массовые операции, фоновые задания и функции
работодателя не входят в v1.

## Требования и установка

- Windows 10/11, macOS или Linux;
- Python 3.11 или новее;
- зарегистрированное приложение HH для сохраняемого OAuth-режима либо действующий
  пользовательский OAuth access token соискателя для env-режима;
- `uv` (рекомендуется) либо другой установщик, способный установить `pyproject.toml`.

В PowerShell из каталога проекта:

```powershell
uv sync --extra test
uv run pytest -p no:cacheprovider
```

В bash/zsh команды те же:

```bash
uv sync --extra test
uv run pytest -p no:cacheprovider
```

`uv.lock` фиксирует полное дерево зависимостей. Секреты и состояние по умолчанию
создаются в `%LOCALAPPDATA%\HHMCP` (Windows),
`~/Library/Application Support/HHMCP` (macOS) или
`${XDG_DATA_HOME:-~/.local/share}/hh-mcp` (Linux). Для изолированной проверки можно
задать `HH_MCP_HOME` абсолютным путём в своей рабочей папке.

В сохраняемом OAuth-режиме master key длиной 256 бит хранится одной версионированной записью системного credential
service; файлы секретов и тексты черновиков шифруются AES-GCM со случайным nonce и
контекстным AAD. На Windows используется Credential Locker, на macOS — Keychain, на
Linux — Secret Service или KWallet. Null/Fail, plaintext, chained и неизвестные
backend'ы отклоняются без перехода к открытому файлу. На Linux должен работать сеанс
D-Bus и разблокированный системный keyring (например, GNOME Keyring или KWallet).
`keyrings.alt` устанавливать не следует. Если `keyring` выбрал Chainer, явно выберите
один системный backend через `PYTHON_KEYRING_BACKEND` и повторите `doctor`.

## Быстрый env-token режим

Для запуска `serve` без `configure`, keyring и браузерного OAuth задайте две переменные:

- `HH_MCP_ACCESS_TOKEN` — действующий **пользовательский OAuth access token
  соискателя**, не application token;
- `HH_MCP_USER_AGENT` — реальный User-Agent с контактным email, например
  `MyHHMCP/0.1 (me@example.com)`.

Если задана только одна переменная, пустое значение или User-Agent без email, сервер
завершается с понятной ошибкой. При наличии обеих переменных env-режим имеет приоритет
над сохранённой конфигурацией. Все read-запросы, включая поиск, справочники, резюме и
историю, используют этот bearer. Keyring, `config.json`, SQLite и auth state для чтения
не инициализируются. Refresh отсутствует: при HTTP 401 замените token в MCP-конфигурации
и перезапустите сервер.

`hh_prepare_application` сначала лениво вызывает `/me`, требует `applicant` и получает
`account_id`. Только после этого создаётся защищённый каталог и отдельный
`environment-state.db`. Письма шифруются AES-256-GCM ключом, полученным через HKDF-SHA256
из access token и account ID. Сам token не записывается в базу. Смена token меняет ключ,
поэтому старые env-черновики становятся недоступны; готовьте их заново. HKDF не защищает
от лица, уже прочитавшего token: имея token и базу, оно может получить тот же ключ.

MCP-конфигурация обычно хранит значения `env` открытым текстом. Это значит, что token
лежит в файле конфигурации как секрет. Если клиент умеет подставлять secret variables
из системного хранилища, используйте эту функцию вместо literal token.

Windows:

```json
{
  "command": "C:\\path\\to\\hh-mcp\\.venv\\Scripts\\python.exe",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "C:\\path\\to\\hh-mcp",
  "env": {
    "HH_MCP_ACCESS_TOKEN": "PASTE_APPLICANT_OAUTH_ACCESS_TOKEN_HERE",
    "HH_MCP_USER_AGENT": "MyHHMCP/0.1 (me@example.com)"
  }
}
```

macOS:

```json
{
  "command": "/Users/YOU/path/hh-mcp/.venv/bin/python",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "/Users/YOU/path/hh-mcp",
  "env": {
    "HH_MCP_ACCESS_TOKEN": "PASTE_APPLICANT_OAUTH_ACCESS_TOKEN_HERE",
    "HH_MCP_USER_AGENT": "MyHHMCP/0.1 (me@example.com)"
  }
}
```

Linux:

```json
{
  "command": "/home/YOU/path/hh-mcp/.venv/bin/python",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "/home/YOU/path/hh-mcp",
  "env": {
    "HH_MCP_ACCESS_TOKEN": "PASTE_APPLICANT_OAUTH_ACCESS_TOKEN_HERE",
    "HH_MCP_USER_AGENT": "MyHHMCP/0.1 (me@example.com)"
  }
}
```

## Сохраняемый OAuth-режим: регистрация и подключение HH

Перед этими командами удалите из окружения обе переменные env-token режима.

1. Войдите на [dev.hh.ru](https://dev.hh.ru) и создайте приложение. Укажите понятное
   название, что приложение локально помогает соискателю искать вакансии и готовить
   индивидуальные отклики, а также действующий контакт разработчика. Соблюдайте
   правила названия и логотипа HH, показанные в кабинете.
2. В поле redirect URI укажите **точно** `http://127.0.0.1:8765/callback`, включая
   протокол, IP, порт и путь. HH проверяет redirect URI относительно зарегистрированного.
   Возможность этого loopback URI нужно подтвердить в кабинете вашего приложения:
   до живого входа она не считается проверенной. Если кабинет не принимает URI,
   остановитесь и согласуйте поддерживаемый точный URI; не заменяйте его произвольно.
3. Скопируйте client ID и client secret. Client secret является секретом. Не вставляйте
   его в чат, JSON конфигурации, аргументы процесса или конфигурацию MCP.
4. Запустите интерактивную настройку:

   ```text
   uv run hh-mcp configure
   ```

   Команда отдельно запросит User-Agent, client ID и скрытый client secret. User-Agent
   должен содержать название и контактную почту, например
   `MyHHMCP/0.1 (me@example.com)`. Client ID и secret сохраняются одной записью,
   зашифрованной AES-256-GCM. Master key остаётся в системном credential service.
   Каталог получает ограниченный ACL на Windows либо владельца текущего UID и режим
   `0700` на macOS/Linux. Символическая ссылка вместо каталога отклоняется.
5. Проверьте локальную настройку без сетевого запроса:

   ```text
   uv run hh-mcp doctor
   uv run hh-mcp auth status
   ```

6. Подключите аккаунт соискателя:

   ```text
   uv run hh-mcp auth login
   ```

   Команда временно слушает только `127.0.0.1:8765`, открывает официальный адрес
   `https://hh.ru/oauth/authorize`, проверяет случайный `state`, PKCE S256 и точный
   callback. После обмена кода `/me` обязан подтвердить роль `applicant`.
7. Первый поиск можно выполнить после подключения MCP-клиента либо через MCP Inspector.
   Для поиска сервер автоматически получает токен приложения по client credentials;
   личные методы используют токен соискателя.

HH refresh token одноразовый и применяется только после истечения access token. Если
результат refresh стал неопределённым из-за обрыва либо не сохранился, сервер не
повторяет refresh автоматически и требует новый `auth login`.

Для локального выхода:

```text
uv run hh-mcp auth logout
```

Команда меняет поколение auth и удаляет локальный пользовательский токен. Она не
отзывает уже отправленный запрос и в v1 не обещает сетевой отзыв токена HH. Для полной
очистки сначала выполните logout, затем вручную удалите каталог данных своей платформы
и соответствующую запись credential service `hh-mcp/master-key/v1`
(account начинается с `installation-` и привязан к абсолютному пути каталога).
При удалении утрачиваются локальный журнал и блокировки неизвестных отправок.

Формат DPAPI из раннего Windows-only прототипа v0.1 не мигрируется. Если такой каталог
уже существует, сохраните его как резервную копию, выберите новый `HH_MCP_HOME` и
повторите `configure`; старые токены потребуется получить новым входом.

## Подключение сохраняемого OAuth-режима к Codex

Сначала выполните `configure`, `doctor` и `auth login` вручную. Затем добавьте сервер
через интерфейс Codex, используя абсолютные пути. Эти образцы не изменяют реальную
конфигурацию.

Windows:

```json
{
  "command": "C:\\path\\to\\hh-mcp\\.venv\\Scripts\\python.exe",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "C:\\path\\to\\hh-mcp",
  "env": {
    "HH_MCP_HOME": "C:\\Users\\YOU\\AppData\\Local\\HHMCP"
  }
}
```

macOS:

```json
{
  "command": "/Users/YOU/path/hh-mcp/.venv/bin/python",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "/Users/YOU/path/hh-mcp",
  "env": {
    "HH_MCP_HOME": "/Users/YOU/Library/Application Support/HHMCP"
  }
}
```

Linux:

```json
{
  "command": "/home/YOU/path/hh-mcp/.venv/bin/python",
  "args": ["-m", "hh_mcp", "serve"],
  "cwd": "/home/YOU/path/hh-mcp",
  "env": {
    "HH_MCP_HOME": "/home/YOU/.local/share/hh-mcp"
  }
}
```

В этих трёх примерах сохраняемого режима в `env` нет client secret и токенов. Для другого MCP-клиента используйте тот же
`command`, `args`, `cwd` и локальный транспорт `stdio`.

## Инструменты MCP

Сервер публикует ровно десять инструментов:

`hh_auth_status`, `hh_search_vacancies`, `hh_get_vacancy`, `hh_get_employer`,
`hh_get_reference`, `hh_list_resumes`, `hh_get_resume`, `hh_list_applications`,
`hh_get_application`, `hh_prepare_application`.

Карточки работодателя и вакансии являются внешним недоверенным содержимым. Текст из
них не меняет правила сервера и не может включить отправку. Неизвестные аргументы MCP
отклоняются усиленной строгой моделью ввода поверх SDK, а сервер проверяет пагинацию, глубину, взаимоисключающие даты,
географические группы и известные конечные значения.

Пример вызова поиска:

```json
{
  "text": "python backend",
  "areas": ["1"],
  "experience": ["between1And3"],
  "work_formats": ["REMOTE"],
  "only_with_salary": true,
  "page": 0,
  "per_page": 20
}
```

`hh_prepare_application` проверяет, что резюме принадлежит текущему аккаунту, вакансия
доступна и не архивна, а в истории и локальном журнале нет известного отклика. Результат
содержит полное точное письмо и его SHA-256. Обычный refresh того же аккаунта сохраняет
черновик; logout, новый login или смена аккаунта требуют подготовить его заново.

## Ручная отправка

Сначала лично проверьте черновик:

```text
uv run hh-mcp application show DRAFT_ID
uv run hh-mcp application status DRAFT_ID
```

Если вы самостоятельно решили отправить показанное содержимое:

```text
uv run hh-mcp application submit DRAFT_ID
```

Команда показывает точное содержимое и требует связанную с SHA-256 фразу, затем
повторно проверяет владельца резюме, вакансию, историю и auth generation и атомарно
резервирует `(account_id, vacancy_id)` непосредственно перед POST. Это удобный ручной
сценарий, а не доказанная
граница от shell-способной модели.

Ответ `201` с `Location` отмечается как `sent`. При сетевом обрыве, 5xx или необычном
ответе операция становится `unknown`; повтор по той же вакансии блокируется даже из
другого черновика и после перезапуска. Совпадение вакансии в истории может помочь
ручной сверке, но не доказывает доставку именно сохранённого письма. В v1 неизвестность
не снимается автоматически. Для direct-вакансии или обязательного теста POST не
выполняется: действие завершается вручную на HH/сайте работодателя.

Тело POST основано на последнем найденном официальном историческом контракте HH от
2023-12-06 (`multipart/form-data`: `vacancy_id`, `resume_id`, `message`). Этот write
контракт отсутствует в скачанном текущем публичном OpenAPI и до регистрации приложения
и живой проверки считается неподтверждённым. Поэтому MCP-write выключен.

## Диагностика

- Redirect URI rejected: сравните URI в кабинете и `config.json` посимвольно; повторите
  `configure`. Не добавляйте query/fragment/userinfo.
- `wrong_account_role`: выйдите на hh.ru из аккаунта работодателя и повторите login под
  соискателем.
- `captcha_required`: откройте официальный URL капчи из интерфейса HH и завершите её;
  сервер не обходит капчу.
- `refresh_inflight` или `requires_login`: исход одноразового refresh не доказан;
  выполните новый login.
- `state_conflict` при отправке: проверьте `application status`; не удаляйте базу, чтобы
  обойти `sending`, `unknown` или `sent`.
- 429: дождитесь указанного HH времени. Сервер не сокращает большой `Retry-After`.

Диагностика не записывает токены, письма и личные ответы. stdout процесса `serve`
зарезервирован для MCP, сообщения CLI и сервера идут отдельно.

## Проверка и источники

Тесты используют HTTP mocks и не отправляют реальные отклики. Живой поиск и личное
чтение требуют зарегистрированного приложения. Реальную отправку можно проверять
только после отдельного решения пользователя по конкретной вакансии и письму.

Контракты и границы уверенности перечислены в [docs/contract-matrix.md](docs/contract-matrix.md),
а выполненные и внешние проверки — в [docs/verification.md](docs/verification.md).
Основные официальные источники: [HH API](https://api.hh.ru/openapi/redoc),
[репозиторий HH API](https://github.com/hhru/api),
[MCP Python SDK v2](https://github.com/modelcontextprotocol/python-sdk) и
[документация Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).
